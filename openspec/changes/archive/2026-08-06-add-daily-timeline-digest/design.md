## Context

系统已经实现按采集任务运行即时发送新增事件的邮件能力：管理员配置 SMTP 通道和任务/人物/事件类型规则，采集完成后创建 `email_delivery_batches` 与明细，`NotificationWorker` 负责事务外发送和持久化重试。现有采集 `Scheduler` 只按 `collection_tasks.next_run_at` 和 `schedule_seconds` 执行，邮件批次与 `task_run_id` 强绑定，不能表达每天固定时刻、跨任务汇总的日报。

本变更跨越 SQLite 数据模型、日历调度、时间窗口计算、通知 Worker、FastAPI、Vue 推送管理、权限审计和运维文档。用户要求人物与发送时间可配置，汇总周期可配置且默认北京时间昨天自然日；日报必须形成按事件发生时间排列的统一时间线，同时不得改变现有即时增量推送语义。

## Goals / Non-Goals

**Goals:**

- 管理员按规则配置关注人物、事件类型、收件人、每日发送时刻和汇总周期，默认北京时间 `08:30`、昨天自然日。
- 以 `Asia/Shanghai` 日历时间可靠触发日报，重启、重复轮询和手工补跑均保持幂等。
- 从统一时间线跨采集任务汇总事件，按发生时间升序生成可核验的纯文本和 HTML 邮件。
- 复用现有 SMTP 配置、凭证保护、发送 Worker、失败重试、权限、审计和投递可观测性。
- 继续使用 FastAPI、Vue 与 SQLite，部署默认关闭或无规则时不产生新邮件。

**Non-Goals:**

- 不改变采集频率、事件抽取、去重、确认或审核流程。
- 不替代现有按任务运行的即时增量邮件，两种通知语义并存。
- 不实现登录用户自助订阅、短信、Webhook 或即时通信通道。
- 不自动连续补发长时间停机期间的全部历史日报；管理员可显式补跑具体业务日期。
- 不迁移到 PostgreSQL、Redis、Celery 或外部定时服务。

## Decisions

### 1. 每条规则保存本地发送时刻，由系统时区解释

新增 `notifications.daily_digest` 默认配置：

```json
{
  "notifications": {
    "daily_digest": {
      "timezone": "Asia/Shanghai",
      "default_send_time": "08:30",
      "default_window_mode": "previous_calendar_day",
      "default_rolling_hours": 24,
      "max_rolling_hours": 168,
      "scheduler_poll_seconds": 30
    }
  }
}
```

每条规则保存经过严格校验的 `send_time`（`HH:mm`）、`window_mode`、`rolling_hours` 和 `send_when_empty`。`send_time` 是规则级可配置项，默认取配置中的 `08:30`；时区由系统配置提供，默认且推荐为 `Asia/Shanghai`。所有 `next_run_at`、窗口边界和运行时间在 API/数据库中以带偏移的 UTC ISO 8601 保存，页面额外显示北京时间。

日历调度以“业务日期 + 本地 `send_time`”计算计划时刻，不使用“上次完成时间 + 86400 秒”，避免执行耗时和重启造成逐日漂移。备选方案是 Linux cron 或 Jenkins 定时调用 API，但会把关键业务状态拆到应用外、降低页面可配置性和可观测性，因此不采用。

### 2. 使用独立日报规则和 Outbox 表，不改写现有即时推送外键

新增以下 SQLite 表：

- `daily_digest_rules`：名称、启停、发送时刻、窗口模式、最近小时数、空日报策略、创建/更新时间和下一计划时刻。
- `daily_digest_rule_persons`：规则与人物多对多关系；日报规则要求至少一行，避免空集合被误解为全部人物。
- `daily_digest_rule_recipients`：规范化收件人列表；每条规则至少一个有效地址。
- `daily_digest_runs`：规则、计划业务日期、计划时刻、窗口起止、状态、候选/投递计数、触发方式和错误摘要；`UNIQUE(rule_id, scheduled_date)`。
- `daily_digest_batches`：运行、收件人、分片、投递状态、尝试次数、稳定 `Message-ID` 和时间；`UNIQUE(run_id, recipient, part_number)`。
- `daily_digest_items`：批次与事件关联；`UNIQUE(run_id, event_id, recipient)`。

现有 `email_delivery_batches.task_run_id` 为非空外键。为兼容旧数据库并降低 SQLite 重建表迁移风险，不把日报强塞进该表；通知模块抽取公共的 SMTP 传输、退避、错误清洗、正文工具和 worker 领取协议，使同一个 `NotificationWorker` 依次处理即时批次与日报批次。投递 API使用 `delivery_kind` 合并展示两类记录。

备选方案是重建现有批次表，增加 `source_kind` 和可空 `task_run_id`；它能统一表结构，但迁移风险和对已部署记录的影响更大，因此不采用。

### 3. 时间窗口使用半开区间并由计划时刻决定

对 `scheduled_date=D`：

- `previous_calendar_day`：窗口为本地时间 `[D-1 00:00, D 00:00)`。
- `rolling_hours=N`：窗口为 `[scheduled_at-N hours, scheduled_at)`。

窗口先在配置时区中计算，再转换为 UTC 持久化和查询。采用半开区间可以让连续自然日或连续等长窗口在边界上不重复。日报运行固化 `window_start` 和 `window_end`，规则后续修改不改变既有运行。

事件窗口归属优先使用 `timeline_events.start_at`；缺失时使用 `created_at`，使时间未知但在窗口内新进入系统的言论仍可被汇总。回退值只用于选择，渲染仍显示“时间未知”，不得把入库时间表述为事件发生时间。

备选方案只按 `created_at` 选择会把旧事件迟到采集与真实发生时间混淆；只按 `start_at` 又会永久遗漏没有精确时间的事件，因此采用明确的优先/回退规则。

### 4. 事件查询跨任务执行并在运行生成时固化明细

日报查询从 `timeline_events`、`public_figures` 和证据/来源关联中选择：

- `person_id` 属于规则人物集合；
- `event_type` 属于规则事件类型；
- `review_status != 'rejected'`；
- 有效选择时间位于固化窗口。

排序键为：

1. `start_at IS NULL`，已知时间优先；
2. `start_at ASC`；
3. `person_id ASC`；
4. `event_type ASC`；
5. `event_id ASC`。

候选在短事务中写入日报明细并按邮件单封上限稳定分片。发送前重新读取事件并跳过已删除或已驳回项；其他内容变更使用发送时的最新值。日报跨所有来源和采集任务汇总，因此不依赖 `task_run_events`，也不会受同一事件追加新证据触发重复即时邮件的规则影响。

### 5. 调度恢复只自动补最近一次到期运行

应用 lifespan 启动日报调度器。每次轮询查找已启用且 `next_run_at <= now` 的规则，以数据库事务插入 `(rule_id, scheduled_date)` 唯一运行。成功或发现既有运行后，按照当前规则发送时间推进到下一未来日历时刻。

若应用停机跨越多个计划日期，只自动创建最近一个到期业务日期；更早日期以安全日志/计数标记为错过，不连续轰炸收件箱。管理员可以按具体业务日期补跑，补跑同样受唯一约束；规则创建或重新启用时把下一次计划设为当前时刻之后，避免补发启用前日报。

备选方案是恢复时逐日追赶所有计划，完整性更高但长期停机会突然发送大量过期邮件。默认只补最近一次更符合每日简报用途，显式补跑保留了修复能力。

### 6. 日报正文复用通知渲染基础并明确时间线语义

邮件使用现有 `notifications.email` SMTP 通道及安全配置。主题包含前缀、规则名、窗口日期/范围和条数；纯文本与 HTML 正文包含窗口说明，并逐条展示事件类型、人物、标题、摘要、北京时间或“时间未知”、地点、确认/审核状态、具体来源和由 `server.base_url` 生成的可选详情链接。

同一运行、收件人和分片使用由日报批次 ID 派生的稳定 `Message-ID`。SMTP 仍是至少一次语义：若服务端已接收但状态未写回，重试可能再次提交相同 `Message-ID`。默认无内容只创建 `empty` 运行；规则启用 `send_when_empty` 时才创建一封“无动态”批次。

### 7. API、页面、权限与审计

在 `/api/v1/notifications/digests` 下提供：

- 规则列表、创建、更新、启停和删除；
- 选项与下一窗口/指定日期预览；
- 指定业务日期补跑；
- 运行列表、详情和终止失败重试。

“推送管理”页面增加“每日时间线邮件”区域，提供人物多选、事件类型、收件人、发送时间、汇总模式、最近小时数、空日报策略、下一运行和实际窗口。发送时间使用 `time` 控件并在提交时规范化为 `HH:mm`。系统配置页面显示非敏感默认值和来源。

读取遵守 `notifications` 页面权限；规则写入、包含收件人的预览、补跑、重试和删除只允许管理员。所有写操作写入审计日志，但不记录 SMTP 凭证或完整收件人列表。自动运行状态可在推送管理和任务中心查看。

## Risks / Trade-offs

- [事件发生时间缺失时按创建时间归属，可能与真实发生日不同] → 邮件明确显示“时间未知”，规格记录回退语义；未来补齐 `start_at` 后由正常事件数据质量流程处理。
- [进程在 SMTP 接收后、状态写回前崩溃可能重复投递] → 复用稳定 `Message-ID`、持久化 outbox 和至少一次语义说明；普通 SMTP 无法保证严格 exactly-once。
- [规则修改恰逢到期扫描可能使用旧或新配置] → 运行创建事务固化规则版本相关的时刻、窗口和事件明细；既有运行不随规则修改重算。
- [长时间停机只自动补最近一次可能漏发更早日报] → 运行/日志标记错过日期，管理员可按日期预览并补跑，避免默认邮件洪泛。
- [同一事件在滚动窗口跨业务日重复出现] → 这是滚动窗口的明确语义；需要无重叠日报时使用默认昨天自然日。
- [日报表与即时推送表并存增加代码路径] → 提取共享 SMTP、渲染、退避和状态机工具，以测试确保两类投递一致；避免高风险重建现有 SQLite 表。
- [规则收件人与全局 SMTP 收件人配置可能造成认知混淆] → 日报规则明确保存自己的收件人，通道配置中的 `to_addresses` 继续只服务既有即时推送；页面分区展示两者用途。

## Migration Plan

1. 以向后兼容迁移创建日报规则、人物、收件人、运行、批次和明细表及索引，不修改现有即时推送记录。
2. 增加 `notifications.daily_digest` 默认配置；没有日报规则时调度器不创建运行或邮件，升级后默认行为不变。
3. 部署后由管理员在现有推送管理页面确认 SMTP 测试通过，再创建人物明确、默认昨日窗口和所需发送时间的日报规则。
4. 先以预览确认下一窗口及事件顺序，再启用规则；首次计划必须晚于启用时刻。
5. 回滚时停止新版本进程后部署旧版本；旧版本忽略新增表，既有即时推送继续工作。再次升级后可恢复未终止的日报批次。
6. 实现、自测和文档完成后提交 GitHub，手工触发 Jenkins 构建并让用户访问部署后的服务验证规则配置、时间窗口和测试邮箱投递。

## Open Questions

无阻塞问题。默认采用每条规则独立收件人、发送时间可配置且默认北京时间 `08:30`、汇总周期可配置且默认昨天自然日、空日报不发送、长期停机只自动补最近一个到期日期。
