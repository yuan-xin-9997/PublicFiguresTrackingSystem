## Context

当前系统的时间线页面（`main.js` 行 625-660）以单页 100 条事件展示，无分页导航；卡片底部显示"可信度"百分比数值，但该数值与确认状态标签（`confirmation_status`）存在部分信息重叠。后端 `GET /api/v1/events` 已完整支持 `page` 和 `page_size` 参数并返回 `total` 计数，仅前端未使用。

推送管理页面（行 824-830）的"投递记录"模块基于旧通知系统的 `email_delivery_batches` / `email_delivery_items` 表。数据库迁移 v9 已废弃旧推送规则和定时增量模块，当前动态推送使用 `daily_digest_*` 表。投递记录表已无新数据写入，现有数据库中的记录数为 0，该模块纯属无效 UI。

冒烟测试 `smoke_live.py` 在每次 Jenkins 构建时创建人物和来源（名称含"冒烟测试"前缀），但不清理，导致测试数据累积。

## Goals / Non-Goals

**Goals:**
- 为时间线添加完整的分页交互（页码导航、每页条数切换、总条数显示）
- 从时间线卡片和详情面板中移除"可信度"百分比显示
- 移除推送管理页面的投递记录模块及其后端 API
- 冒烟测试结束后清理创建的测试数据

**Non-Goals:**
- 不修改后端分页逻辑（已完整实现）
- 不删除 `email_delivery_batches` / `email_delivery_items` 数据库表（仅移除接口和 UI，保留历史数据）
- 不修改 `percent()` 函数（其他模块可能使用）
- 不修改事件置信度计算逻辑（`extractor.py`）

## Decisions

### 1. 分页交互设计：服务器端分页 + 页码导航

**选择**: 在现有服务器端分页基础上，前端添加标准页码导航控件。

**替代方案考虑**:
- *无限滚动*: 不适合需要精确跳转和了解总条数的场景，且与现有后端分页契约不匹配。
- *仅显示"加载更多"按钮*: 无法跳转到特定页面，不适合大量数据浏览。

**分页控件布局**:
- 左侧：每页条数选择器（20/50/100/200，默认 20)
- 右侧：页码按钮组（上一页/页码/下一页）+ 页码跳转输入框
- 中间：总条数信息

**状态管理**:
- 添加 `page` ref（默认 1）
- 筛选条件变更时重置 `page = 1`
- `page_size` 不再硬编码为 100，改为可配置

### 2. 可信度移除：仅前端删除显示

**选择**: 仅从模板中删除可信度渲染代码，不动后端 `confidence` 字段和数据库。

**理由**: 后端 `confidence` 字段仍被 `extractor.py` 计算和存储，可能在未来分析场景中使用。仅移除前端展示即可满足当前的 UI 简化需求。

### 3. 投递记录模块移除：全链路清理

**选择**: 移除前端模板、状态管理、后端 API 端点、任务运行中的旧投递统计查询，以及 `notifications.py` 和 `scheduler.py` 中相关的 `EmailWorker` 旧任务轮询逻辑。

**替代方案考虑**:
- *仅隐藏 UI*: 保留死代码，增加维护负担。
- *删除数据库表*: 破坏已有部署的迁移兼容性，且表设计已固化在 schema 中。

**清理范围**:
- 前端: 投递记录面板模板、`deliveryFilters`、`deliveryTotal`、`selectedDelivery`、`openDelivery()`、`retryDelivery()`、`loadPage()` 中的投递 API 调用
- 后端: 三个投递记录端点（行 1046-1119）、任务运行查询中的 `notification_batches`/`notification_items`/`notification_error` 统计（行 547-549）
- 测试: 删除投递记录相关测试用例

### 4. 冒烟测试清理：finally 块保证清理

**选择**: 在 `smoke_live.py` 中使用 try/finally 确保测试结束后删除创建的人物和来源。

**理由**: 即使测试失败，也能保证清理执行，避免残留数据累积。

## Risks / Trade-offs

- **[风险] 外部系统可能依赖已删除的投递记录 API** → 当前部署环境无外部调用者，且该 API 仅用于页面内前端调用，无外部集成。
- **[风险] 分页切换时筛选条件变更可能丢失当前页码** → 通过 watch 中重置 `page = 1` 确保一致性。
- **[风险] 移除可信度可能影响需要该信息的用户** → 后端保留 `confidence` 字段，如后续需要可恢复显示。
