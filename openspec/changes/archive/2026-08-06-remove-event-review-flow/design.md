## Context

系统当前把事件质量控制拆成确认状态、审核状态、置信度、证据链和审核中心。采集或分析产生的事件可能被标记为 `pending`、`needs_review`、`approved` 或 `rejected`，管理员在审核中心或事件详情中执行通过、驳回等动作。README、需求规格、系统设计、Vue 导航、权限管理、仪表盘统计、事件详情和通知筛选都引用了这一流程。

用户现在希望移除审核中心和事件审核流程，让所有采集到的事件默认通过并直接进入时间线；后续处置从“审核通过/驳回”改为“在时间线删除不需要保留的事件”。本变更仍需保留公开来源证据、确认状态、冲突标记、置信度和审计日志，避免把数据质量信息一并抹掉。

## Goals / Non-Goals

**Goals:**

- 新创建、导入、重分析或合并产生的事件默认进入可见时间线，等价于通过审核。
- 删除审核中心页面、导航、页面权限项、审核队列统计和事件详情审核按钮。
- 在时间线和事件详情提供管理员删除事件能力，并记录操作审计。
- 保持事件确认状态、置信度、证据链、来源冲突、人工锁定和北京时间展示。
- 调整即时推送、定时增量推送、每日时间线邮件和仪表盘统计，使其不再依赖待审核流程。
- 同步更新需求、设计、README、测试、冒烟脚本和 Jenkins 校验。

**Non-Goals:**

- 不改用 SQLite 以外的数据库。
- 不新增外部审核、工单或队列服务。
- 不重做事件抽取、去重、人物归属或内容质量算法。
- 不实现复杂的事件编辑、合并、拆分工作台；已有能力只按移除审核流程做兼容调整。
- 不为普通用户增加删除、修改或管理权限。

## Decisions

### 1. 保留 `review_status` 字段但将新事件统一写为 `approved`

新事件的默认审核状态统一规范化为 `approved`，并移除自动写入 `pending` 或 `needs_review` 的路径。现有数据库中的 `pending`、`needs_review` 可在迁移或启动规范化中改为 `approved`；`rejected` 历史记录默认保持不可见或按已删除/跳过处理，避免重新发布管理员明确驳回过的内容。

备选方案是重建 SQLite 表并删除 `review_status` 字段。该方案能彻底清理模型，但会影响通知、日报、历史记录和现有迁移，风险高于收益；保留字段并弱化语义更适合增量部署。

### 2. 用事件删除替代驳回工作流

时间线卡片和事件详情为管理员显示删除按钮。后端提供事件删除 API，要求管理员权限、二次确认对应的前端交互和审计日志。删除应复用或扩展现有事件删除语义：删除事件主体记录及可安全清理的关联明细，或使用现有软删除字段时从所有查询中排除。

备选方案是在时间线保留“驳回”按钮并把驳回视为删除。该方案会继续暴露审核概念，与用户要删除审核流程的目标冲突，因此不采用。

### 3. 移除页面入口，兼容后端旧接口

前端删除审核中心页面组件、路由/页面枚举、导航项、权限管理选项、仪表盘待审核跳转和事件详情审核动作。后端可删除审核 API，或保留 `/events/{id}/review` 返回 `410 Gone`/兼容错误，防止旧客户端静默改变数据。

备选方案是隐藏页面但保留 API 继续可用。这样会留下未被测试的隐形工作流，并让权限与审计口径继续复杂化，因此只保留必要兼容响应。

### 4. 查询、统计和通知以“未删除事件”为主

时间线、地图、搜索、人物详情、仪表盘和任务中心不再把 `pending` 或 `needs_review` 作为待处理队列。通知和日报候选不再要求人工通过；它们应选择未删除且未被历史驳回保留的事件，发送前仍复检事件是否已删除。

备选方案是完全忽略所有历史 `review_status`。这会让已驳回内容重新进入推送和日报，违反用户对删除/驳回内容不应再传播的合理预期，因此历史 `rejected` 需要兼容处理。

### 5. 文档把质量控制从“审核流程”改为“质量标识 + 删除处置”

需求和设计文档需要移除审核中心作为必备页面，改写流程图、权限表、接口列表、验收标准、冒烟测试和审计日志说明。质量信息继续展示为确认状态、冲突、置信度和证据链，用户通过删除处理明显不需要的事件。

## Risks / Trade-offs

- [低置信或冲突事件默认可见，可能增加误读风险] → 保留确认状态、冲突标识、置信度和来源证据，并在时间线提供删除处置。
- [历史 `rejected`、`pending`、`needs_review` 数据语义复杂] → 迁移时将待审核类状态规范为通过，保留驳回类内容不可见或跳过，并增加回归测试。
- [删除操作比驳回更具破坏性] → 限制管理员权限、前端二次确认、审计日志和测试覆盖；如已有软删除能力，优先采用软删除。
- [移除页面权限项可能影响已有用户配置] → 权限同步时忽略或清理 `review` 页面，不阻断登录；管理员默认页面集合自动更新。
- [旧 API 客户端仍调用审核接口] → 返回明确的废弃响应或兼容错误，并在 README 和设计说明中记录迁移方式。

## Migration Plan

1. 增加兼容迁移或启动修复，把 `pending`、`needs_review` 等待审核状态规范化为 `approved`；保留 `rejected` 历史内容不进入默认查询和通知。
2. 更新默认页面权限，移除审核中心页面项，并确保已有用户配置中残留页面不会导致前端报错。
3. 部署新后端，确认事件创建、任务运行、通知 Worker 和日报调度均按未删除事件工作。
4. 部署新前端，确认导航无审核中心、时间线管理员可删除事件、普通用户只读。
5. 回滚时旧版本仍可读取保留的 `review_status` 字段；但已删除的事件不会自动恢复。
6. 完成自测后提交 GitHub，手工触发 Jenkins 构建，并让用户在构建后的服务验证采集默认显示、无审核中心和时间线删除。

## Open Questions

无阻塞问题。默认策略为：新事件写入 `approved`，待审核历史转为 `approved`，历史驳回内容不重新发布，事件删除仅管理员可执行。
