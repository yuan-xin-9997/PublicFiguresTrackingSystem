## Context

系统当前有两条邮件链路：`notifications.py` 在采集任务结束后按 `task_run_events` 为即时规则创建 `email_delivery_batches/items`；`daily_digest.py` 则按事件发生时间的自然日或滚动小时窗口创建日报运行，再由同一个 `NotificationWorker` 发送。前者会随采集频率产生零散邮件，后者无法表达“上次发送截止后才入库的事件”，尤其会漏掉发生日期较早但刚被采集的事件。

本变更需要跨越 SQLite 迁移、规则 API、调度线程、持久化 outbox、邮件模板、Vue 推送管理、权限审计和运维文档。约束是继续使用单机 FastAPI/Vue/SQLite，不引入消息队列；SMTP 故障不能影响采集事务；北京时间必须明确展示；升级后不能把存量事件突然推送给现有收件人。

## Goals / Non-Goals

**Goals:**

- 让同一套事件推送规则可选择即时或定时增量模式，并让现有规则无行为变化地升级。
- 每个计划窗口只选择自上一切分高水位以来新入库的匹配事件，包括发生时间早于窗口的迟到事件。
- 通过事务性运行快照、唯一约束和持久化批次，在崩溃、重复轮询和 SMTP 重试下做到不漏入队、不重复建批次。
- 支持一个或多个北京时间每日发送时刻、预览、立即汇总、运行记录、失败重试、权限和审计。
- 复用现有 SMTP 安全配置、邮件 Worker、稳定 `Message-ID`、分片和指数退避。

**Non-Goals:**

- 不实现任意 cron、秒级间隔、短信、Webhook、即时通信或登录用户自助订阅。
- 不回溯规则启用前或重新启用前的事件，不改变事件抽取、去重或审核语义。
- 不合并或删除现有“每日时间线邮件”；它仍服务于按发生时间生成日报的场景。
- 不承诺 SMTP 端严格 exactly-once；SMTP 接收后、状态写回前崩溃仍可能用同一 `Message-ID` 重复提交。

## Decisions

### 1. 在现有规则上增加投递模式，现有记录迁移为即时

`notification_rules` 增加 `delivery_mode`（`immediate` / `scheduled_incremental`）、`send_times_json`、`enabled_at`、`next_run_at` 及游标字段。迁移为旧行填充 `immediate`，即时入队函数只处理即时规则，新增调度器只处理定时规则。这样任务、人物、事件类型和全局收件人语义保持一致，管理页面也无需维护两套重叠规则。

备选方案是把定时规则做成第三套独立规则表；它会复制即时规则的范围、权限和表单逻辑，并使用户难以在两种模式间切换，因此不采用。

### 2. 使用 `task_run_events` 的词典序高水位，而不是事件发生时间

游标表示三元组 `(created_at, run_id, event_id)`。每次运行在 SQLite 事务快照中读取当前最大三元组作为上界，并选择满足 `lower < tuple <= upper`、任务/人物/类型匹配且事件未被审核驳回的关联行。已知发生时间只用于邮件展示和稳定排序，不参与增量归属。

`task_run_events` 已只记录采集运行首次创建的事件，能够延续即时推送“不因去重合并旧事件重复通知”的语义；三元组用运行和事件 ID 打破相同时间戳的并列，不依赖 SQLite 隐式 `rowid`，也无需重建现有表。

备选的 `timeline_events.created_at` 无法可靠保留采集任务范围；按计划时间或事件发生时间查询则可能因提交竞争或迟到入库产生漏项。

### 3. 区分“窗口已切分”与“邮件已发送”

新增 `scheduled_notification_runs`、`scheduled_notification_batches` 和 `scheduled_notification_items`。创建运行时在一个 `BEGIN IMMEDIATE` 短事务内完成：锁定/重读规则、确定上下界、插入不可变候选明细、按当前有效收件人和分片上限创建批次、推进规则游标并计算下一计划时刻。游标在运行成功持久化时推进，而不是等 SMTP 成功后推进。

因此失败邮件继续重试原批次，而后续计划窗口从新的下界开始，不会重新选择失败运行的事件。运行和批次保留收件人、窗口、事件集合及稳定 `Message-ID` 快照；SMTP 配置变更不重写已经建立的批次。每个计划槽使用 `UNIQUE(rule_id, scheduled_at)`，每个明细使用 `UNIQUE(run_id, event_id, recipient)`。

若把游标绑定到发送成功，一名收件人的持续失败会让后续窗口重叠并让其他收件人收到重复内容；若发送时动态查询，则重试内容会漂移。两者均不采用。

### 4. 规则生命周期采用“无隐式回溯”策略

创建并启用定时规则、从即时切换为定时、重新启用，或修改任务/人物/事件类型范围时，把游标初始化为当时全局最大高水位并重算 `next_run_at`。这意味着停用期间和范围变更前的事件不会自动补发。仅改名称或发送时刻时保留游标；更改发送时刻只影响未来计划槽。

立即汇总操作使用当前游标到当前高水位创建 `manual` 运行并推进游标。页面必须在范围重置前提示，API 响应和审计日志记录 `cursor_reset`，避免管理员误以为会回溯。

备选的自动补历史会在首次上线、重新启用或扩大范围时造成邮件风暴，故不采用。

### 5. 使用北京时间日历调度，并只自动补最近一期

规则存储去重并排序后的 `HH:mm` 列表，配置层提供 `timezone`（默认 `Asia/Shanghai`）、`default_send_times` 和 `scheduler_poll_seconds`。计算下一次运行时把本地日历时刻转换为 UTC 保存，页面同时展示北京时间。轮询发现多个错过槽位时只为最近一个到期槽位建运行，然后从当前时间计算下一槽位；更早窗口已包含在同一个高水位增量中，无需逐槽补发。

相较固定秒数间隔，日历调度更符合“每天几点”的用户预期，也可正确处理系统暂停和时区规则。任意 cron 表达式增加验证、可解释性和 UI 成本，不在本次范围内。

### 6. 复用 Worker，但保持三类批次的数据边界

`NotificationWorker.process_once()` 在即时批次、定时增量批次和日报批次之间按到期时间/ID 做公平选择，并调用各自的消息构建与运行状态刷新函数。定时邮件按事件发生时间（未知置后）、人物、类型、事件 ID 稳定排序，标题和正文明确标出“入库增量窗口”和事件数量；事件在发送前被删除或失去可见性时记为 `skipped`，不动态用别的事件补位。

复用一个通用大表会需要高风险迁移现有投递历史；保持独立运行表能让窗口语义、状态统计和回滚更清晰，同时仍共享 SMTP 发送代码。

### 7. API、页面、权限与可观测性沿用现有推送管理边界

规则 CRUD 扩展 `delivery_mode` 和 `send_times`；新增预览、立即汇总、运行列表/详情和批次重试端点。拥有 `notifications` 页面权限的用户可查看脱敏配置和运行记录，只有管理员可创建、修改、启停、立即汇总或重试。所有写操作记录规则 ID、模式、计划时刻、是否重置游标和结果，不记录 SMTP 凭证或邮件正文。

任务中心与应用日志记录调度运行 ID、上下界、候选/批次/跳过计数和清洗后的错误摘要。配置值进入系统配置页面但敏感字段继续脱敏。

## Risks / Trade-offs

- [计划切分后 SMTP 长期失败，用户看到后续窗口先到达] → 每个运行独立重试并展示窗口/状态；管理页突出失败运行，允许管理员重试，邮件主题携带窗口截止时间。
- [同一事件可能由异常数据产生多条 `task_run_events`] → 运行候选按 `event_id` 去重，并用运行明细唯一约束兜底；任务范围匹配任一关联即可。
- [规则编辑与调度轮询竞争] → 使用短 `BEGIN IMMEDIATE` 事务重读规则版本；更新规则同时重算游标/下一运行，唯一约束阻止重复运行。
- [SQLite 写锁延迟采集] → 只在事务内选择 ID、写运行/批次和游标，不进行 SMTP、模板渲染或网络操作；使用既有 busy timeout 和索引。
- [大量事件使单封邮件过大] → 沿用 `max_events_per_message` 分片，并限制预览样例数量；明细查询分页。
- [全局 SMTP 收件人变更造成运行间收件人不同] → 创建运行时快照收件人；已创建运行保持不变，后续运行使用新配置并记录审计。
- [至少一次 SMTP 语义可能产生重复提交] → 使用稳定 `Message-ID`、明确文档化该边界并提供投递记录，不宣称端到端 exactly-once。

## Migration Plan

1. 通过可重复 SQLite 迁移给 `notification_rules` 增加模式、时间、游标和下次运行字段，创建定时运行/批次/明细表及索引；旧规则全部标记为 `immediate`。
2. 部署兼容新旧数据的后端和前端；首次启动仅初始化定时规则的当前高水位，不创建存量运行。保留现有即时和日报表，不删除历史记录。
3. 更新 `app.json` 示例和代码默认值，但 Jenkins 增量部署不得覆盖服务器已有 `src/config/app.json`；缺失字段由代码默认值补齐。
4. 运行数据库迁移、后端/前端测试和真实服务烟雾测试，确认即时规则仍可用，再由管理员按需把规则切换为定时增量。
5. 更新 README、需求规格说明书、系统设计说明书、Jenkinsfile 和 systemd 运维说明；提交 GitHub 后手工触发 Jenkins 构建并让用户在部署服务验证。

回滚时先停止调度线程，再回退应用代码；新增表和列保留以避免数据丢失，旧代码会忽略它们。切换回即时模式不会重放定时运行，失败批次可在恢复新版本后继续处理。

## Open Questions

无阻塞问题。默认采用每日一个北京时间发送时刻（由配置提供），管理员可在规则中增加多个时刻；现有即时规则不会自动切换。
