## Why

当前邮件推送在采集任务每新增一条事件后立即排队，频繁采集时会产生大量零散邮件；现有每日时间线邮件又按事件发生时间取窗口，不能可靠覆盖“自上次推送截止点以来新入库”的迟到事件。系统需要让管理员按固定北京时间批量推送新增事件，同时保持失败可重试、事件不漏发且不因窗口重叠重复入队。

## What Changes

- 为事件推送规则增加“即时”与“定时增量”两种投递模式；现有规则继续保持即时模式，避免升级后静默改变行为。
- 定时增量规则支持配置一个或多个北京时间每日发送时刻，并继续沿用任务、人物、事件类型和收件人范围。
- 每次计划运行固定一个事件入库高水位，只汇总上一个已切分高水位之后、当前高水位之前新建且符合规则的事件；以入库顺序而非事件发生时间划窗，使迟到入库的历史事件仍能进入下一封邮件。
- 新规则启用时把当时高水位作为起点，默认不补发存量；规则范围或模式发生实质变化时重置起点并记录审计，避免意外回溯。
- 在同一 SQLite 事务中创建不可变运行、候选事件明细并推进“已切分”游标；邮件失败只重试该运行的持久化批次，不回退游标或重新选择事件。
- 调度器重启后补建最近一个到期运行，重复轮询、进程重启和手工触发均通过唯一约束保持幂等；空窗口只记录运行，不发送邮件。
- 推送管理页面增加投递模式、发送时刻、下一次运行、上次窗口、事件数与状态展示，并支持预览和对失败批次重试。
- 同步补充数据库迁移、API、后台调度、邮件模板、权限审计、单元/集成/前端/烟雾测试，以及需求规格说明书、系统设计说明书、README、Jenkins 质量门禁和 systemd 运维说明；部署不得覆盖已有 `src/config/app.json`。
- 非目标：本次不新增短信、Webhook 或即时通信通道，不开放任意 cron 表达式，不自动补发启用规则前的历史事件，也不改变事件抽取与去重逻辑。

## Capabilities

### New Capabilities

- `scheduled-incremental-event-push`: 定时增量规则、基于入库高水位的无遗漏窗口、持久化运行与批次、幂等调度、失败重试、管理页面及权限审计要求。

### Modified Capabilities

无。现有主规格中尚无邮件推送能力；本能力在不改变现有即时规则默认行为的前提下扩展当前已实现的邮件投递基础设施。

## Impact

- 后端：FastAPI 推送规则 API 和模型增加投递模式及发送时刻；新增定时增量调度/运行服务，并复用现有 `NotificationWorker`、SMTP 配置、稳定 `Message-ID` 和退避重试。
- 前端：Vue“推送管理”页面增加定时增量配置、窗口预览、下一次运行和运行记录；仍沿用 `notifications` 页面权限，只有管理员可修改规则或触发操作。
- 数据库：继续使用 SQLite；扩展 `notification_rules`，新增或扩展定时运行、运行事件与收件人批次表，并以规则、计划时刻/窗口和事件明细唯一约束保证幂等，无需更换数据库。
- 配置：在 `notifications.email` 下补充可配置的定时调度轮询、时区和默认发送时刻；环境相关值不得硬编码，页面和 API 不返回 SMTP 密钥。
- 兼容性：既有即时规则、每日时间线邮件及其历史投递记录保持可用；新增规则默认从启用时刻开始收集，升级不产生历史邮件风暴。
- 交付：更新 README、需求规格说明书、系统设计说明书、配置示例、测试和 `src/JenkinsConfig/Jenkinsfile`；实现完成并自测后提交 GitHub、手工触发 Jenkins，再由用户访问部署服务验证。
